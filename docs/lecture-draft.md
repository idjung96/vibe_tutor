# AI 에이전트 개발팀 구성하기 — Skill과 하네스로 Owner 개입 최소화하기

> 초보 개발자를 위한 강의 초안 (large 프로파일 기준, 90~120분)

---

## 0. 강의 개요

**한 줄 요약**: Claude Code에 skill(작업 규칙)과 하네스(역할·게이트·가드레일)를 깔면,
요구사항만 입력해도 10개 역할의 AI 에이전트가 서로 의견을 주고받으며 자동으로 개발하는
"팀"이 만들어진다. Owner(사람)는 정말 중요한 결정에만 개입한다.

**학습 목표**
- skill과 하네스가 각각 무엇이고 왜 필요한지 이해한다.
- Stage-Gate 방식으로 에이전트 팀이 협업하는 흐름을 따라갈 수 있다.
- 결정 등급(A/B/C)과 가드레일이 Owner 개입을 어떻게 최소화하는지 설명할 수 있다.
- 직접 설치해서 작은 프로그램 하나를 자동 개발시켜 본다.

---

## 1. 왜 "팀"이 필요한가 — 문제 정의

### 1.1 출발점: "자리를 뜰 수가 없다" (개인 업무 관점)

이 팀을 만든 직접적인 이유는 거창한 게 아니다. AI 코딩 도구를 쓰면 분명
일을 시키는 건데, **조금만 진행되면 확인 요청이 와서 엔터를 쳐 줘야 한다.**
"이렇게 할까요?" → 엔터 → 30초 뒤 "다음은 이렇게 할까요?" → 엔터 —
결국 코딩을 맡긴 게 아니라 **AI 옆에 붙어 앉아 엔터 치는 일**을 하게 된다.
자리를 비우면 작업이 멈춰 있고, 회의 다녀오면 첫 질문에서 그대로 서 있다.

원인을 뜯어보면 AI가 물어보는 것의 대부분은 사람이 답할 필요가 없는 것들이다.
함수 이름, 파일 위치, 라이브러리 선택 — 기준만 미리 정해 주면 스스로 결정할 수
있는 문제다. 반대로 정말 물어봐야 할 것(요구사항 변경, 삭제, 비용)은 다른 사소한
질문에 섞여 들어와 구분되지 않는다.

그래서 목표를 이렇게 다시 세웠다: **"묻지 않고도 안전하게 진행할 수 있는 구조"를
만들어, 요구사항을 주고 자리를 떠도 되게 하자.** 사람에게 오는 질문은 미리 정한
목록(C등급)에 있는 것만, 그것도 영향 표와 추천안이 정리된 형태로 — 돌아와서
`답: 2` 한 줄 적으면 다시 알아서 굴러가게. 이 요구를 채우기 위한 장치가
결정 등급, 게이트, 가드레일이고, 그것을 담는 그릇이 "팀"이다.

### 1.2 두 번째 목표: "누가 시켜도 같은 코드" (조직 관점)

두 번째 배경은 회사다. 같은 회사에서 같은 AI 도구를 써도 **결과물은 쓰는 사람마다
다르다.** A가 시키면 camelCase에 print 디버깅, B가 시키면 snake_case에 로거,
C는 테스트를 아예 안 만들고 넘어간다. 코딩 컨벤션과 테스트 작성 방식이
개인의 프롬프트 실력과 그날의 대화에 좌우되기 때문이다. 결국 코드 리뷰에서
매번 같은 지적이 반복되고, AI가 만든 코드라 양은 많은데 스타일은 제각각이라
유지보수 비용이 오히려 늘어난다.

그래서 두 번째 목표는 이것이었다: **팀 하네스를 설치하면 누가, 어떤 프롬프트로
시켜도 같은 컨벤션·같은 로깅 규칙·같은 테스트 구조의 코드가 나오게 하자.**
규칙을 사람의 머리(프롬프트 습관)가 아니라 프로젝트의 파일(skill)에 두면,
`code-convention`·`logging-rule`·`test-design` 스킬이 매 작업마다 동일하게
주입되므로 결과가 사람에 의존하지 않는다. 초보가 시켜도 시니어의 관행이 적용되고,
관행을 바꾸고 싶으면 프롬프트 교육이 아니라 **스킬 파일 한 곳만 고치면**
팀 전체에 반영된다. 하네스는 개인의 자동화 도구인 동시에
**조직의 개발 표준 배포 수단**이다.

### 1.3 혼자 일하는 AI의 문제들

AI에게 "이거 만들어줘" 한 마디로 시키면 생기는 일:

- **자기 채점 문제**: 코드를 짠 AI가 자기 코드를 스스로 "잘 됐다"고 판정한다. 팔이 안으로 굽는다.
- **테스트 조작**: 테스트가 실패하면 코드가 아니라 테스트를 고쳐 버린다.
- **범위 폭주**: 시키지 않은 기능까지 만들고, 요구사항은 빠뜨린다.
- **끝없는 질문 또는 위험한 독단**: 사소한 것까지 물어보거나, 반대로 DB를 지우는 결정을 혼자 내린다.

사람 개발팀이 이 문제를 푸는 방법이 이미 있다: **역할 분리, 코드 리뷰, 테스트 우선,
결재 라인**. 이걸 AI 에이전트에 그대로 이식한 것이 이 하네스다.
정리하면 배경은 세 겹이다: 1.1 자리를 떠도 되게(개인의 시간), 1.2 누가 시켜도
같게(조직의 표준), 1.3 맡겨도 사고 안 치게(품질·안전). 믿고 맡길 구조가 없으니
계속 확인시키는 것이고, 구조를 만들면 셋이 함께 풀린다.

## 2. 두 가지 재료: Skill과 하네스

### 2.1 Skill = 개발 관행 주입서

Skill은 "이 작업은 이렇게 하라"는 절차·규칙 문서다. 에이전트가 해당 작업을 할 때
자동으로 읽고 따른다. 이 하네스에는 6개가 들어 있다:

| Skill | 주입하는 관행 |
|---|---|
| `team-dev` | 팀 개발 절차 전체(정본). 아래 4장에서 상세히 다룸 |
| `code-convention` | 변수·함수 이름, 함수 크기(40줄), 매직넘버 금지 |
| `logging-rule` | print 금지, logger 사용, 비밀값 로그 금지 |
| `test-design` | 테스트 이름에 R번호, 엣지 4종(빈 입력·잘못된 타입·경계값·중복) |
| `lib-research` | 새 라이브러리는 추측 금지 — 조사해서 `dev-agent-team/libs/`에 기록 후 사용 |
| `ui-design` | UI 단계의 디자인 토큰·접근성(WCAG)·반응형 명세 |

핵심 아이디어: **"코드를 이렇게 짜라"고 매번 말하는 대신, 규칙을 파일로 깔아두면
에이전트가 알아서 지킨다.**

### 2.2 하네스 = 역할 + 절차 + 강제 장치

하네스는 skill만으로 부족한 부분 — "누가, 어떤 순서로, 무엇을 못 하게" — 를 채운다.

- **헌법 (`AGENTS.md`)**: 모든 에이전트가 따르는 공통 규칙.
- **역할 (subagent 10종)**: 각자 좁은 임무와 출력 형식이 정의된 전문가들.
- **상태 파일 (`dev-agent-team/`)**: 계획·결정·질문이 전부 파일로 남는다. 대화가 아니라 파일이 팀의 기억이다.
- **가드레일 (hook)**: 규칙 위반을 "부탁"이 아니라 **기계적으로 차단**한다.

이 하네스는 Claude Code뿐 아니라 Codex, opencode에서도 동작한다(설치기가 에이전트별로
렌더링). 이 강의는 Claude Code 기준으로 설명한다.

### 2.3 동작 원리 — 결국 전부 "프롬프트"다. 단, 주입 시점과 범위가 다르다

LLM은 파일을 "설치"하지 않는다. 하네스와 스킬의 정체는 **적절한 순간에 모델의
컨텍스트(프롬프트)에 텍스트로 끼워 넣어지는 문서**다. 그런데 끼워 넣어지는
**시점·범위·강제력**이 4계층으로 다르고, 이 차이가 설계의 전부다:

| 계층 | 파일 | 언제 프롬프트에 들어가나 | 누구의 컨텍스트에 |
|---|---|---|---|
| 헌법 | `CLAUDE.md`(→`@AGENTS.md` import) | **세션 시작 시 항상** 자동 로드 | 메인 세션 |
| 역할 | `.claude/agents/<role>.md` | 해당 subagent **호출 시점**에 시스템 프롬프트로 | 그 subagent의 **새 컨텍스트만** |
| 스킬 | `.claude/skills/<name>/SKILL.md` | frontmatter의 description이 현재 작업과 맞을 때 **온디맨드** 로드 | 그 작업을 하는 세션 |
| 가드레일 | hook 스크립트 + settings.json | **프롬프트에 안 들어감.** 도구 호출 시 별도 프로세스로 실행 | (LLM 밖) |

코드로 반영되는 경로를 따라가면:

```
Owner: "요구사항 입력"
 → 메인 세션 컨텍스트 = [CLAUDE.md/AGENTS.md] + 사용자 입력
 → "팀 개발" 작업 감지 → team-dev SKILL.md 텍스트가 컨텍스트에 추가됨
 → SKILL 절차의 "coder를 호출한다" 실행
   → 새 컨텍스트 생성 = [coder.md 시스템 프롬프트] + goal + 테스트 파일 경로
   → coder가 Write 도구 호출 (여기서 코드가 파일로 생성됨)
     → 도구 실행 직전 hook(protect_tests.sh)이 셸에서 돌아 경로 검사
     → 통과하면 파일 기록, exit 2면 도구 호출 자체가 거부되고 stderr가 모델에 전달
 → coder의 텍스트 출력(FILE:/COUNT:...)만 메인 세션으로 반환
```

즉 "코드로 반영"이란: 프롬프트가 모델의 **도구 호출(Write/Edit/Bash)**을 특정 방향으로
유도하고, hook이 그 도구 호출을 통과/차단하는 것이다. 프롬프트는 확률적 유도,
hook은 결정적 차단 — 그래서 가드레일만은 프롬프트가 아니라 코드다.

### 2.4 그렇다면 왜 하나의 거대 프롬프트가 아니라 별도 파일인가

"어차피 다 프롬프트라면 CLAUDE.md에 전부 써 넣으면 되지 않나?" — 안 되는 이유가
곧 동작 원리다:

1. **컨텍스트 경제 (온디맨드 로딩)**: 컨텍스트 창은 유한하고, 관련 없는 규칙이 많을수록
   모델의 지시 이행률이 떨어진다. 스킬을 별도 파일로 두면 description만 상주하고
   본문은 **필요한 작업 때만** 로드된다. UI 없는 단계에서 ui-design 스킬은 단 한 줄도
   컨텍스트를 차지하지 않는다.
2. **컨텍스트 격리 (역할 파일 = 깨끗한 새 프롬프트)**: subagent는 메인 세션의 대화
   이력을 물려받지 않고 자기 역할 파일 + 전달받은 최소 입력으로 시작한다.
   coder에게 goal과 테스트만 주는 것이 가능한 이유다. 전부 한 프롬프트였다면
   coder가 planner의 고민, Owner의 잡담까지 다 보게 되고, "역할 경계"는 흐려진다.
   checker의 자기 채점 금지도 격리가 있어야 성립한다 — 코드를 짠 기억이 없는
   컨텍스트가 채점하니까.
3. **선택적 조합 (렌더링)**: 별도 파일이라서 init.sh가 프로파일(small/large) ×
   에이전트(claude/codex/opencode)별로 필요한 조각만 골라 깔 수 있다. 같은
   `roles/coder.md.tmpl` 하나가 Claude에선 `.claude/agents/coder.md`, opencode에선
   `.opencode/agents/coder.md`로 렌더된다. 거대 단일 프롬프트였다면 에이전트마다
   전체를 복사·수정해야 한다.
4. **망각 방지 (재주입 가능)**: 긴 세션에서 앞부분 지시는 희석된다. 파일로 있으면
   단계가 끝날 때마다 "CLAUDE.md와 PLAN.json을 다시 읽는다"(절차 13번)로 규칙을
   컨텍스트 앞으로 다시 끌어올 수 있다. 프롬프트 한 번 치고 마는 방식으론 불가능.
5. **강제력의 분리**: "하지 마라"는 프롬프트는 잊히거나 무시될 수 있다. 그래서
   어겨선 안 되는 규칙(테스트 수정 금지, Owner 답변 대기)만은 프롬프트 밖의
   실행 코드(hook)로 뺐다. 파일이 나뉘어 있으니 "유도(스킬)"와 "차단(훅)"을
   각각 고치고 검증(`verify_hooks.sh`)할 수 있다.

강의 한 줄 요약: **"별도 파일"은 저장 방식이 아니라 주입 제어 방식이다 —
무엇을(선택), 언제(온디맨드), 누구에게(격리) 프롬프트에 넣을지를 파일 단위로 제어한다.**

## 3. 팀 구성 — 10개 역할 (large 프로파일)

### 실무 5역할 (개발 사이클의 손발)

| 역할 | 임무 | 쓸 수 있는 것 |
|---|---|---|
| **planner** | 요구사항을 3~7단계로 나누고, 단계별 결정(A/B등급)을 내림 | 계획·질문 파일만 작성 |
| **tester** | 단계의 수용 기준마다 테스트 작성. **코드보다 먼저** | `tests/`에 새 파일만 |
| **coder** | 테스트를 통과시키는 코드만 작성. goal 밖은 금지 | 구현 코드. `tests/` 수정 불가 |
| **checker** | 테스트 **전체** 실행 후 PASS/FAIL만 판정. 추측 금지 | 실행·판정만 |
| **documenter** | 제품 README·문서 작성 | 문서만 |

### 관리 4역할 (large 전용 — 품질과 방향의 머리)

| 역할 | 임무 | 개입 시점 |
|---|---|---|
| **lead** (팀장) | 방향·우선순위 결정, 백로그 그루밍, 절차 개선 제안(IMPROVE) | 계획 전 + 매 단계 시작 |
| **critic** (비평가) | planner 결정에 반론. AGREE/REVISE/ESCALATE 판정 | planner 결정 직후 |
| **reviewer** | 코드·테스트코드 리뷰. 지적만 하고 직접 안 고침 | 테스트 PASS 후, merge 전 |
| **security** | 비밀값 하드코딩·인젝션·위험 호출 점검 | reviewer 다음, merge 전 |

### +1: designer (UI 단계에만, 양 프로파일 공통)

UI가 있는 단계에서 디자인 명세(`DESIGN.md`)만 작성. 코드는 coder가 명세대로 구현.

### 단일 작성자 원칙 (강조 포인트)

공유 상태 파일(PLAN, DECISIONS, BACKLOG, DIRECTION 등)은 **메인 세션만** 쓴다.
subagent는 자기 산출물만 만들고, 제안은 출력으로 보고만 한다.
→ 여러 에이전트가 같은 파일을 동시에 고쳐 꼬이는 사고를 원천 차단.

## 4. 동작 흐름 — Stage-Gate 한 바퀴

### 4.1 큰 그림

```
[인터뷰] → Gate 0 (Owner: 요구사항 확인)
[lead 방향설정 → planner 계획] → Gate 1 (Owner: 계획 승인)
┌─ 단계 반복 ──────────────────────────────┐
│ 브랜치 생성                                │
│ lead(초점) → planner(결정) → critic(반론) │
│ → (UI면 designer) → tester → 커밋         │
│ → coder → checker                         │
│ → PASS: reviewer → security → merge       │
│ → FAIL: coder 재시도 (RETRY_LIMIT=5회)     │
└──────────────────────────────────────────┘
[documenter] → Gate 4 (Owner: 최종 확인)
```

Owner가 반드시 등장하는 곳은 **Gate 0, 1, 4와 C등급 질문**뿐이다. 나머지는 전부 자동.

### 4.2 단계 하나를 자세히 (시연 대본용)

1. **`git checkout -b stage/2-user-save`** — 단계마다 브랜치.
2. **lead 호출**: "이번 단계 초점은 B-3 입력검증. 이유: 지난 단계 메모에 2회 반복."
   → 출력 형식이 `DIRECTION:/PRIORITIES:/GROOMING:/IMPROVE:/ESCALATE:`로 고정.
3. **planner 호출**: 이 단계의 결정을 내리고 등급 분류.
   - A등급(함수명, 파일 구조) → 그냥 결정하고 한 줄 보고.
   - B등급(DB 스키마, 라이브러리 선택) → 결정하고 `DECISIONS.md`에 기록.
   - C등급(요구사항 변경, 삭제, 비용, 배포, 보안, GPL) → **멈추고 Owner에게 질문**.
4. **critic 호출**: planner 결정에 반론.
   - `AGREE` → 진행. `REVISE` → planner가 대안 반영해 재결정(최대 5회).
   - `ESCALATE` → C등급으로 승격, Owner 합의.
5. **tester 호출**: done_check마다 정상 케이스 + 엣지 4종. 테스트 먼저 커밋.
6. **coder 호출**: goal과 done_check만 받고 테스트를 통과시키는 코드 작성.
   모르는 라이브러리? 추측 대신 "lib-research 필요: {이름}" 보고하고 멈춤.
7. **checker 호출**: `pytest` 등으로 **전체** 실행. 출력은
   `RESULT:/TYPE:/FAILED:/REASON:/LOG:` 형식 고정.
8. **결과 분기**:
   - `PASS` → reviewer(코드·테스트 리뷰, CHANGES면 coder가 수정) → security(RISK면 수정,
     심각하면 ESCALATE) → merge, TEST_LOG 갱신.
   - `NEW_FAIL` → coder에게 로그를 주고 재시도. 5회 실패 시 C등급.
   - `REGRESSION` → "이전 기능을 깨뜨렸다. **새 코드만 고쳐라. 테스트는 고치지 마라.**"
   - coder가 "기존 테스트가 틀렸다"고 주장 → 자동으로 C등급 (스스로 판단 못 하게).

### 4.3 왜 이 순서인가 (초보자용 해설)

- **테스트가 코드보다 먼저**: coder가 채점 기준을 못 바꾼다. 시험문제를 먼저 봉인하는 것.
- **checker는 짠 사람이 아님**: 자기 채점 금지. 실행 결과만 보고 추측 금지.
- **reviewer/security는 PASS 후**: 돌아가는 코드에만 리뷰 비용을 쓴다.
- **critic은 결정 직후**: 코드를 짜기 전에 잘못된 결정을 잡는 게 제일 싸다.

## 5. Owner 개입 최소화의 핵심 장치

### 5.1 결정 등급 A/B/C — "언제 사람에게 물을 것인가"의 명문화

| 등급 | 예시 | 처리 |
|---|---|---|
| A | 함수명, 파일 구조 | 에이전트가 결정, 한 줄 보고 |
| B | DB 스키마, API 형식, 라이브러리 | 에이전트가 결정 + critic 검증 + 기록 |
| C | 요구사항 변경, 삭제, 비용, 외부 배포, 보안, GPL, 두 갈래 해석 | **정지하고 Owner에게 질문** |

포인트: "모호하면 물어봐라"가 아니라 **C 목록에 있으면 C, 없으면 알아서**.
기준이 목록이라 에이전트가 과잉 질문도, 위험한 독단도 못 한다.

### 5.2 C등급 질문의 형식 — Owner의 판단 비용까지 줄인다

`dev-agent-team/OWNER_QUESTION.md`:
- 선택지 2~3개, 각각 **영향 표 5항목 고정**(기능/코드 변경/일정/테스트/되돌리기).
- 코드 변경은 grep으로 실제 사용처를 세어 파일 개수로.
- 하나에 (추천) 표시 — 이유는 안 적음. **표가 이유다.**
- Owner는 파일에 `답: 2` 한 줄만 적으면 끝.

### 5.3 가드레일(hook) — 부탁이 아니라 차단

- **`block_on_owner_question.sh`**: OWNER_QUESTION.md에 `답: 숫자`가 없으면
  모든 도구 사용을 exit 2로 차단. → C등급 질문을 무시하고 진행하는 것이 **불가능**.
  답이 적히면 자동 해제. (Owner 개입 = 파일에 숫자 하나 적기)
- **`protect_tests.sh`**: 기존 테스트 파일 수정 시도를 차단(py/go/rs/js·ts 공통).
  → "테스트를 고쳐서 통과"라는 꼼수가 기계적으로 봉쇄.
- **deny 목록**: force push, `rm -rf`, `git reset --hard`, `python -c` 등 위험 명령 금지.
- 같은 로직이 Claude=hook, Codex=hooks.json, opencode=guard.js로 3중 구현되어 있다.

강의 메시지: **프롬프트로 "하지 마"라고 쓰는 것과 hook으로 exit 2를 내는 것의 차이**.
LLM은 규칙을 잊을 수 있지만 hook은 잊지 않는다.

### 5.4 상한선 — 무한 루프 방지

- `RETRY_LIMIT=5`: coder 재시도 5회 실패 → C등급으로 사람에게.
- `MAX_CHECKER_CALLS=15`: 한 단계에서 checker 15회 초과 → C등급.
- reviewer 지적 5회 초과 → 남은 지적은 BACKLOG에 적고 진행(완벽주의 루프 방지).

## 6. 에이전트끼리 어떻게 의견을 주고받는가

핵심: **대화가 아니라 파일과 고정 출력 형식으로 소통한다.**

### 6.1 통신 채널 = `dev-agent-team/` 상태 파일

| 파일 | 누가 쓰나 | 무엇 |
|---|---|---|
| REQUIREMENTS.md | 메인 세션 | R번호 붙은 요구사항 |
| PLAN.json / PLAN.md | 메인(planner 산출) | 단계·goal·done_check·covers |
| DECISIONS.md | 메인 세션 | 모든 결정 기록 (감사 추적) |
| BACKLOG.md | 메인 세션 | 단계 밖 발견사항 (B-번호) |
| DIRECTION.md | 메인(lead 산출) | 팀 방향·우선순위 |
| OWNER_QUESTION.md | 메인(planner 산출) | C등급 질문 ↔ Owner의 "답:" |
| TEST_LOG.md | 메인 세션 | 단계별 테스트 결과 |
| PROCESS.md | 메인 세션 | 승인된 절차 개정 (P번호, append-only) |
| libs/*.md | 메인 세션 | 라이브러리 조사 결과 |

상태가 전부 파일에 있으므로 **세션이 끊겨도, 모델을 바꿔도(small↔large) 이어서 개발**할 수 있다.

### 6.2 의견 교환 패턴 3가지 (강의 하이라이트)

**패턴 1 — 제안과 반론 (planner ↔ critic)**
```
planner: "세션 저장은 SQLite로 결정 (B등급)"
critic:  VERDICT: REVISE
         REASON: 요구사항 R3가 동시 접속 100명 — SQLite 쓰기 잠금 병목
         ALTERNATIVE: PostgreSQL 또는 R3 수치의 재확인
planner: (대안 반영해 재결정) → critic: AGREE → DECISIONS.md에 합의 근거 기록
```
합의가 안 되고 모호·고위험이면 ESCALATE → Owner에게. **에이전트끼리 5회까지 토론하고,
그래도 안 되면 사람에게** — 이것이 개입 최소화의 균형점.

**패턴 2 — 지적과 수정 (reviewer/security → coder)**
```
reviewer: RESULT: CHANGES
          FINDINGS: app.py:42 - 매직넘버 86400 - SECONDS_PER_DAY 상수로
coder:   (고침. 테스트는 못 건드림) → checker 재실행 → reviewer: OK
```
reviewer는 **직접 고치지 않는다**. 지적만. 고치는 건 coder. 역할 침범 금지.

**패턴 3 — 발견과 이관 (coder → BACKLOG → lead/planner)**
```
coder: "BACKLOG: 로그인 모듈에 중복 코드 발견 (goal 밖이라 안 고침)"
메인 세션: BACKLOG.md에 B-7로 기록
lead(다음 단계): "B-7 우선순위 상. 이번 단계 초점으로."
```
goal 밖 문제를 **즉흥 수정하지 않고** 파일로 넘긴다. 범위 폭주 방지 + 정보 손실 방지.

### 6.3 출력 형식이 고정된 이유

모든 역할의 출력이 `RESULT:/FINDINGS:/VERDICT:` 같은 고정 키로 끝난다
("다른 말은 쓰지 않는다"). → 메인 세션이 다음 분기를 **기계적으로** 판단할 수 있고,
장황한 설명 속에 판정이 묻히는 일이 없다.

### 6.4 팀이 스스로 일하는 방식을 고친다 (large의 백미)

lead가 재발 신호(같은 메모 2회 반복, RETRY_LIMIT 도달 등)를 감지하면
IMPROVE 제안 → 절차 변경은 고위험이므로 C등급으로 Owner 승인 →
승인되면 `PROCESS.md`에 P-번호로 append → 이후 모든 역할이 헌법보다 PROCESS.md 우선.
**회고와 프로세스 개선까지 자동화**되어 있지만, 마지막 승인은 항상 사람.

## 7. 실습 — 30분 데모

### 7.1 설치

```bash
git clone <이 저장소>
./init.sh --profile large --agent claude ~/projects/demo-todo
cd ~/projects/demo-todo
claude
```

설치되는 것: `AGENTS.md`(헌법), `CLAUDE.md`, `.claude/agents/`(역할 10개),
`.claude/skills/`(스킬 6개), `.claude/settings.json`(hook·deny),
`dev-agent-team/hooks/`(가드 스크립트). 설치 끝에 `verify_hooks.sh`가 14항목 자동 검증.

### 7.2 실습 과제 예시

"CLI 할 일 관리 프로그램"을 시킨다. 관찰 포인트:

1. **Gate 0**: 인터뷰 4문항(누가/필수기능 3개/곤란한 상황/배포 여부) → REQUIREMENTS.md
2. **Gate 1**: PLAN.md를 쉬운 말로 보여주며 "1. 네, 시작 (추천) 2. 수정" — 숫자만 답하면 됨
3. 단계가 도는 동안 **Owner는 구경만** — lead/planner/critic/tester/coder/checker/reviewer가 릴레이
4. **일부러 C등급 유발**: 중간에 "저장 형식을 바꿔줘"라고 요청
   → C등급 처리 → OWNER_QUESTION.md의 영향 표 → `답: 1` 기입 → hook 자동 해제 시연
5. **가드레일 시연**: 세션에서 기존 테스트 파일 수정을 시켜보기 → exit 2 차단 메시지 확인
6. **Gate 4**: R번호별 통과 표 + "직접 실행해서 확인해 보세요"

### 7.3 Owner가 한 일 총정리 (강의 마무리 슬라이드)

| 시점 | Owner의 행동 |
|---|---|
| Gate 0 | 질문 4개 답하기 + "맞나요?"에 1 |
| Gate 1 | 계획 보고 1 |
| C등급 (발생 시) | 영향 표 보고 `답: N` 한 줄 |
| Gate 4 | 실행해 보고 확인 |

**그 외 전부 — 설계 토론, 테스트, 구현, 리뷰, 보안 점검, 회고 — 는 팀이 알아서.**

## 8. 정리와 Q&A 예상 질문

- **핵심 교훈 3가지**
  1. 규칙은 프롬프트가 아니라 **skill 파일 + hook**으로 — 잊지 않고, 어길 수 없게.
  2. 역할을 좁게 쪼개고 **작성자/검증자를 분리** — 자기 채점 금지.
  3. 사람의 개입 지점을 **등급표와 게이트로 명문화** — 과잉 질문도 독단도 없앤다.

- **Q. small 프로파일과 뭐가 다른가?** 온프레미스 소형 모델용. 실무 5역할+designer만 있고
  lead/critic/reviewer/security가 없다. 상태 파일 형식은 동일해서 중간에 프로파일을
  바꿔도 무손실 인수인계가 된다(호환성 계약).
- **Q. 가드레일을 에이전트가 우회하면?** hook은 도구 호출 자체를 차단하므로 프롬프트
  차원의 우회가 안 된다. 단 에이전트별 강제력 차이가 있어(Codex 훅 불안정 등)
  헌법 규칙 병행 + 컨테이너 실행을 권장.
- **Q. 토큰 비용이 크지 않나?** 역할별 컨텍스트가 좁고(coder는 goal+테스트만 받음),
  단계마다 컨텍스트를 정리하고 재시작하므로 긴 단일 세션보다 오히려 효율적일 수 있다.
- **Q. 다른 에이전트(Codex/opencode)에서도 되나?** 된다. 헌법은 AGENTS.md 공통,
  가드레일만 에이전트별 방식(hook / hooks.json / guard.js)으로 깔린다.
